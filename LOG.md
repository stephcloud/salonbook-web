- Auth and proxy built on `feat/auth-proxy`. The login handler stores the token in an httpOnly `sb_token` cookie (30 minutes) and returns only the user. `/api/proxy/*` adds the Authorization header, rejects `..` segments, blocks `auth/login` (it would return the token), clears the cookie on 401 and retries once. `/login` and `/register` (client or salon owner) exist, with `/salons` and `/dashboard` placeholders. Real API behaviour checked with curl: wrong password is 401 `{"detail":"invalid credentials"}`, bad register input is 422 with a `detail` list. POST and PATCH are not retried after a timeout, so a slow request cannot be applied twice. `maxDuration` is 300 on the new routes (Hobby ceiling with Fluid Compute); the existing home page still says 60.

- Contract checked against the live API with two throwaway accounts (`WIZARD PROBE client` / `WIZARD PROBE owner`, emails `wizard-probe-<role>-1228723922@example.com`, created 2026-10-11) and the existing "Smoke Salon" fixture (its stylist has 15-minute slots from 9:00 AM). Findings the openapi does not state:
  - Slots: an owner token gets 200 (any role may read slots). Creating a booking as an owner is 403 `{"detail":"forbidden"}`.
  - 201 returns `starts_at` and `ends_at` in UTC (`...Z`); we format them through `time.ts`. The request must carry an offset: `2026-10-13T09:00:00` is 422 `timezone_aware`; `starts_at` in the past is 422 with a plain string `detail` ("starts_at must be in the future"), not a list.
  - A taken, overlapping or off-grid slot is 409 "That time slot is no longer available. Please pick another time." An unknown stylist is 404 `not found`.
  - Reaching 3 unpaid pending bookings is ALSO 409 ("You already have 3 unpaid pending bookings. Complete one or wait 15 minutes for it to expire."). The only difference from a taken slot is the message, so `classifyBookingError` (`src/lib/booking-errors.ts`) matches `/pending bookings/i`. If the backend wording changes, the limit would be shown as "slot taken". A machine-readable `code` field on these 409s would remove this fragility.
  - 401 has `{"detail":"invalid credentials"}`, also on malformed requests (auth runs first); our proxy turns it into "Please sign in again." and clears the cookie.
- Probe data cleaned up: all 4 probe bookings were cancelled (`POST /bookings/{id}/cancel`). The two probe accounts remain in the live database; they have no salons. Dev-server checks through the real proxy also passed (slots 200, create 201, same slot 409, owner 403, no cookie 401).
