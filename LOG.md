## 2026-10-11 (pay and callback)

- Pay step built on `feat/pay-callback` (based on `feat/booking-wizard`): `/bookings/[id]/pay` (countdown from the booking's own `created_at` plus 15 minutes, corrected by the server clock so a wrong device clock does not matter; Pay button calls `POST /bookings/{id}/pay`, saves the booking id in sessionStorage, then goes to the Paystack link), `/payment/callback` (reads only sessionStorage, never the URL; polls `GET /bookings/{id}` every 2 seconds for up to 60 seconds, stops on a result, on the time limit and on unmount; clears the saved id on a final result) and a minimal read-only `/bookings` list so the links on these pages work. No new dependencies.
- Contract checked against the live API with the WIZARD PROBE client (Smoke Salon, test mode; all probe bookings cancelled or expired afterwards). What the openapi does not say:
  - `GET /bookings/{id}` is `payment_status: null` and `payment_amount: null` before paying; after `POST /pay` it is `payment_status: "pending"`, `payment_amount` = the deposit in kobo.
  - `POST /pay` is idempotent: a second call returns the same payment and the same `https://checkout.paystack.com/<code>` link (reference `sb_...`, currency `NGN`).
  - There is no `expires_at`. After 15 minutes an unpaid booking becomes `status: "cancelled"` with `cancelled_at: null`; a booking the client cancels has `cancelled_at` set. So `cancelled_at === null` means "the hold expired". A booking whose payment was started but never completed also becomes `cancelled`, and its `payment_status` stays `"pending"`.
  - `POST /pay` for a cancelled or expired booking is 409 "This booking can no longer be paid for." Someone else's booking is 403 `forbidden`; an unknown id is 404 `not found`; a malformed id is 422 (a list). The same 403/404 apply to `GET /bookings/{id}`. Cancelling an already cancelled booking returns 200.
  - `GET /bookings` is sorted by start time, latest first (corrected on 2026-10-11: it is not sorted by creation time).
  - Not yet observed: the pay error for an already paid booking, and the URL Paystack returns the browser to (needs one real Paystack test payment). The pay page handles any 409 by re-reading the booking, so it should not depend on the exact wording.
- Safety decisions: the Pay button only follows an `https` link on `paystack.com` (or a subdomain); anything else shows an error and nothing is saved. The callback page takes no input from the URL. A saved id must be a UUID. Raw server error text (5xx) is never shown.
- Still to verify by hand on the deployed site (the Paystack redirect cannot reach `localhost`): one real test payment, then confirm the browser lands on `/payment/callback` and flips to confirmed via the webhook. The countdown and Pay button were checked against the live API through the dev server only by fetching the rendered pages (no real browser click-through).

- Review fixes for the pay step: a created timestamp with no zone is read as UTC (tested under two device time zones); a "failed" payment is only shown after it has stayed failed for 10 seconds, because paying again reuses the same payment record and the API can still say "failed" for a moment before the webhook marks it paid; a 401 while checking stops quietly (login redirect); checking continues in a background tab; the Pay button resets when the page is restored with the Back button; at zero the pay page says "Checking your booking..." until the re-read answers, so a last-second payment never flashes "expired"; new screens move focus to their heading and are announced; calmer wording ("We did not receive your deposit", "Please do not pay again", salon phone is a `tel:` link); sentence case "My bookings"; the list shows pending holds that ran out as Expired; `Panel` and the action row are their own components; payment pages have their own loading and error screens.
